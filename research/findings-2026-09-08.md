## 2. indic-parler-tts Deep Configuration Analysis {#2-indic-parler-tts-config}

### 2026-09-08 — Optimal Configuration for indic-parler-tts Tamil Output
**Subagent question:** What are the optimal configuration settings, known limitations, and tuning strategies for ai4bharat/indic-parler-tts to maximize Tamil audio quality?

**Answer:**

### Temperature (currently 0.3) — TOO LOW
- Official INFERENCE.md streaming example explicitly sets `temperature=1.0`
- Official HuggingFace Space uses `do_sample=True` with no temperature (defaults to 1.0)
- All model card examples use `do_sample=True` without temperature override
- **0.3 is almost certainly too low**, producing flat/robotic prosody
- **Recommended**: Start at 1.0, tune to 0.85-0.9 if excessive variability

### TOP_K (currently 50) — REMOVE IT
- No official example uses top_k at all
- Codebook has 1024 entries; top_k=50 severely restricts valid continuations
- **Recommended**: Remove top_k=50 entirely

### REPETITION_PENALTY (currently 1.15) — REMOVE IT
- No official code example uses repetition_penalty
- Audio codec tokens naturally repeat (sustained sounds, vowels, silences)
- 1.15 penalty causes: premature truncation, micro-stutters, pitch shifts
- **Recommended**: Remove entirely (set to 1.0 / omit)

### VOICE_DESCRIPTION — TOO VERBOSE
- Official Space Tamil example: "Jaya speaks with a slightly low-pitched, quite monotone voice at a slightly faster-than-average pace in a confined space with very clear audio."
- Current description is 60+ words — official patterns use 15-30 words
- **Recommended**: "Jaya speaks with a slightly low-pitched voice at a moderate pace. The recording is very high quality, clear and close-sounding, with no background noise."

### Sample Rate — 44,100 Hz Confirmed
- `ylacombe/dac_44khz/config.json`: `"sampling_rate": 44100`
- Frame rate: 86 tokens/second (44100 / prod([8,8,4,2]) = 44100/512 ~ 86.13)

### Attention Implementation — Keep "eager"
- Official Space uses `attn_implementation="eager"`
- Community reports SDPA/FA2 are broken with indic-parler-tts (Discussion #10)
- SDPA gives 1.4x speedup for base parler-tts but not confirmed for indic variant

### Known Failure Modes
- Audio truncation for sequences > 10-12 seconds (AI4Bharat confirmed)
- Tamil NSS of only 75.48% (lowest tier among supported languages)
- Tamil has limited training data (52.25 hours only)
- Slow inference: 5-6 seconds for 10 tokens on AWS G5

### Token Estimation
- Frame rate = 86 tokens/second
- CHARS_PER_SEC = 13.0 is NOT an official value — Tamil glyphs encode more phonetic content per character than English
- Official Space doesn't estimate max_new_tokens at all
- **Recommended**: Use frame_rate directly, cap at 12 seconds max per chunk

### Chunk Size
- Official Space uses 25 words per chunk with nltk.sent_tokenize
- Project's 100 chars ~ 15-20 Tamil words ~ 5-8 seconds (within safe range)
- **Recommended**: Switch to word-count-based chunking (20-25 words)

### Mixed Precision
- Official Space uses `torch.bfloat16` (better numerical stability)
- Current project uses float16 — switch to bfloat16 on Ampere+ GPUs

### Tamil Emotion Support
- Tamil officially supports emotion prompts: Command, Anger, Narration, Conversation, Disgust, Fear, Happy, Neutral, Sad, Surprise

**Not verified:**
- Exact optimal temperature range for Tamil (no ablation study exists)
- Whether top_p produces better results than no filtering
- Whether repetition_penalty specifically causes Tamil artifacts
- Whether torch.compile works with indic variant

**Other discoveries:**
- Description encoder is google/flan-t5-large
- Encoder output caching in project is a smart optimization not in official examples
- DAC codec has num_codebooks: 9, codebook_size: 1024
- Tamil emotion descriptions could improve naturalness

## 3. Tamil/Tanglish Text Normalization & G2P {#3-text-normalization}

### 2026-09-08 — Text Normalization and G2P for Tamil/Tanglish
**Subagent question:** What are the best practices and tools for text normalization and G2P for Tamil, English (Indian accent), and Tanglish text in TTS systems?

**Answer:**

### IndicNLP Library — Tamil Text Normalization
- `TamilNormalizer` class at `indicnlp.normalize.indic_normalize.TamilNormalizer(lang='ta')`
- Handles: two-part dependent vowel signs, pulli/virama, colon→visarga
- Base class handles: ZWJ/ZWNJ removal, ZWSP→space, BOM removal
- Install: `pip install indic-nlp-library` (v0.92, MIT)
- Requires: `INDIC_RESOURCES_PATH` env var pointing to indic_nlp_resources

### Tamil Number-to-Words — CRITICAL GAP
- Current normalizer ALWAYS passes `lang="en"` to `indic_num2words` (normalizer.py:100,104,106,115,119,139,181)
- `indic_numtowords` v1.1.0 FULLY supports Tamil: `num2words(42, lang='ta')` -> "நாற்பத்து இரண்டு"
- **Bug in library**: Decimal numbers crash in Tamil (`KeyError: '.5'`)
- Fix: Use `lang='ta'` for Tamil text, handle decimals with digit-by-digit approach

### Tamil Unicode Normalization
- Tamil Unicode block: U+0B80-U+0BFF — current TAMIL_RE correctly covers this
- Tamil numerals: ௧-௯ (U+0BE7-U+0BEF), ௰(10), ௱(100), ௲(1000)
- **GAP**: normalizer's LONG_DIGIT_RE and SHORT_NUM_RE only match Arabic digits, not Tamil numerals
- Conversion: `ord(ch) - 0x0BE6` maps Tamil digit to Arabic, then feed to indic_num2words

### Code-Switching Detection
- **AI4Bharat IndicLID**: 47 classes including `tam_Tamil`, `tam_Latn`, `eng_Latn`
- F1-score: 0.98 (native), 0.75 (roman)
- **Simple heuristic**: Unicode script detection (Tamil block vs Latin) per word

### Sentence Segmentation
- IndicNLP `sentence_tokenize.sentence_split(text, lang='ta')` — auto-detects danda vs period
- Tamil does NOT use danda — falls to period-based splitting
- Current chunker has partial Tamil support (3 Tamil conjunctions: மற்றும், ஆனால், எனவே)

### Tamil Abbreviation Expansion — GAPS
- No Tamil-specific abbreviations handled (செ.மீ, கி.மீ, ரூ, திரு, திருமதி, முனைவர்)
- Only one Tamil override exists: `"Journey": "ஜர்னி"` (normalizer.py:45)

### G2P Tools
- Aksharamukha: 120 scripts, Tamil→IPA (Roman IPA Indic), `pip install aksharamukha` (AGPL-3.0)
- IndicXlit: Roman→Tamil and Tamil→Roman, 68.10% top-1 accuracy, `pip install ai4bharat-transliteration` (MIT)
- IndicNLP Syllabification: `orthographic_syllabify(word, 'ta')` for syllable boundaries

### Loanword Handling
- IndicXlit converts English loanwords to Tamil script: "computer" -> "கம்ப்யூட்டர்"
- 11M params transformer model

**Not verified:**
- Aksharamukha Python API exact syntax (docs require JS)
- IndicLID word-level classification performance for Tanglish
- Whether indic-parler-tts has internal text normalization

**Other discoveries:**
- `indic_numtowords` decimal bug in Tamil mode
- Pronunciation override "Journey": "ஜர்னி" shows English→Tamil mapping concept exists
- AI4Bharat ecosystem (IndicXlit, IndicLID, IndicNLP) all MIT-licensed, designed to work together
- Bhashini platform aggregates all AI4Bharat models as hosted APIs

## 4. Audio Post-Processing Pipeline {#4-post-processing}

### 2026-09-08 — Audio Post-Processing for SOTA TTS Quality
**Subagent question:** What audio post-processing techniques and tools can achieve SOTA quality for TTS output from Parler-TTS at 44.1kHz?

**Answer:**

### Priority-Ranked Pipeline:

1. **pyloudnorm** — LUFS normalization (CPU, <1ms, zero GPU)
   - `pip install pyloudnorm` (MIT, 782 stars)
   - ITU-R BS.1770-4 loudness algorithm
   - Target: -16 LUFS for web/mobile voice-over
   - Works at any sample rate including 44.1kHz

2. **scipy high-pass filter** — Remove DC offset/sub-bass (CPU, <1ms)
   - Butterworth filter at 60-80Hz cutoff
   - `scipy.signal.butter(4, 60, btype='highpass', fs=44100, output='sos')`
   - Already available via pyloudnorm dependency

3. **Resemble-Enhance** — Speech enhancement (GPU, 0.5-2s per chunk)
   - `pip install resemble-enhance` (MIT, 2.4K stars)
   - Denoiser + Enhancer modules, trained on 44.1kHz (native match)
   - Denoiser only is faster (~100-500ms)
   - Full enhancer uses CFM, not real-time (2-10s)

4. **Crossfade stitching** — Replace hard 100ms silence gaps
   - Overlap-add with equal-power (sqrt cosine) fade curves
   - 20-50ms overlap typical for speech
   - Variable pause by punctuation: period ~150ms, comma ~80ms, question ~200ms

### Vocoder Post-Processing — NOT RECOMMENDED
- Parler-TTS decodes through built-in DAC decoder end-to-end
- Intercepting intermediate representation requires modifying model internals
- Waveform→mel→waveform round-trip would be lossy and likely degrade quality
- BigVGAN v2 has 44kHz model (122M params, 240x real-time on A100) but requires mel spectrograms
- Vocos has no pre-trained 44.1kHz model

### Super-Resolution — NOT NEEDED
- 44.1kHz Nyquist is 22.05kHz, beyond most human hearing
- Upsampling to 48kHz adds inaudible 22.05-24kHz band
- Resemble-Enhance can restore missing upper harmonics if needed

### Dynamic Range Compression
- Light compression: threshold -20 to -15 dBFS, ratio 2:1, attack 10-20ms, release 100-200ms
- Implement with numpy, CPU only, sub-ms
- Or use `pedalboard` by Spotify for GPU-accelerated DSP chain

### De-reverb — NOT NEEDED
- Parler-TTS generates clean direct speech when prompted correctly
- Description already includes "completely free of background noise"

### Sample Rate & Transport
- Stay at 44.1kHz (model's native rate), let browser resample to 48kHz
- Stay with PCM16 (96dB dynamic range, sufficient for speech)

### Real-Time Budget (alongside TTS on single GPU):
| Technique | Real-time? | GPU? | Latency |
|---|---|---|---|
| pyloudnorm | YES | CPU | <1ms |
| scipy HPF/LPF | YES | CPU | <1ms |
| numpy fade/crossfade | YES | CPU | <1ms |
| Dynamic compression | YES | CPU | <1ms |
| DeepFilterNet | YES | CPU/GPU | ~10-30ms |
| Resemble-Enhance denoiser | MARGINAL | GPU | ~100-500ms |
| Resemble-Enhance full | NO | GPU | ~2-10s |

**Not verified:**
- Whether Parler-TTS output has artifacts benefiting from denoising (needs listening tests)
- DeepFilterNet with 44.1kHz audio resampled to 48kHz
- BigVGAN 44kHz model exact frequency match
- Spotify pedalboard primary source verification

**Other discoveries:**
- Double-trimming issue: frontend trims leading silence (threshold 0.0008) differently from backend (threshold 0.005)
- No scipy in requirements.txt — pyloudnorm would add it
- DeepFilterNet works only at 48kHz — requires resampling
- VoiceFixer handles 44.1kHz natively but is older (2021)

## 6. Streaming Architecture Optimization {#6-architecture}

### 2026-09-08 — Streaming Architecture and Performance Optimization
**Subagent question:** What are the best architectural patterns and optimizations for low-latency, high-quality streaming TTS in Movio-2's FastAPI + WebSocket architecture?

**Answer:**

### CRITICAL BUG: Streaming is Defeated
- `server.py:121-131`: The `async for` loop collects ALL streaming pieces into a `pieces` list, concatenates, THEN sends entire sentence as one `send_bytes()`. None of the intermediate chunks reach the client during generation.
- TTFA = time to generate entire first sentence, NOT the intended ~300ms
- **Fix**: Send each streaming chunk immediately via `send_bytes()` inside the loop

### Model Serving — Key Changes Needed
1. **bfloat16 > float16**: Every official example uses bfloat16. float16 risks NaN cascades from logit overflow. Switch on Ampere+ GPUs.
2. **Attention**: Keep "eager" — SDPA/FA2 reported broken for indic variant (Discussion #10)
3. **torch.compile**: mode="default" gives 1.4x speedup, but incompatible with streaming. mode="reduce-overhead" gives 3-4x but requires static shapes.
4. **Batching**: Streamer rejects batch_size > 1. Useful only for non-streaming cache warming.

### Thread Safety Bug
- `tts_engine.py:206`: `engine = TTSEngine()` is module-level singleton
- No lock on `model.generate()` — two concurrent WebSocket handlers corrupt each other's state
- **Fix**: Add `asyncio.Semaphore(1)` or `asyncio.Lock` around generation

### WebSocket Protocol — Already Optimized
- Binary frames (no base64 overhead)
- With per-chunk streaming: 26KB frames at 0.3s chunks — efficient

### Caching — Adequate but Not Persistent
- 200 entries LRU, ~431KB per entry (~84MB max), lost on restart
- Persistent options: Redis for binary data, disk for warm cache on cold start
- Semantic caching impractical for TTS

### Frontend Audio — Correct Pattern
- BufferSource scheduling with audio clock timing is correct (per web.dev)
- AudioWorklet better for truly continuous streaming (after fix)
- 100ms gap between sentences is intentional for prosody

### Missing Production Features
- No health check endpoint
- No GPU memory monitoring or OOM recovery
- No concurrent request queuing
- Static files should be served by reverse proxy

**Not verified:**
- Exact frame_rate for indic-parler-tts (config.json gated)
- torch.compile compatibility with indic variant
- Flash Attention 2 support

**Other discoveries:**
- Warmup only uses Tamil — should warm both languages
- Local streamer class may be outdated vs upstream ParlerTTSStreamer
- Fixed seed (42) trades variety for cacheability
- Text auto-tagging happens client-side (split pipeline)
- Model ~4-6GB total GPU usage in float16 with KV-cache
